# guard-core -> onchain: inspectTransfer refuses every @x402/svm payment

**Blocking:** live Solana x402 payments (GC-3), and so INT-4/INT-5 for paid_fetch.

`@x402/svm` 2.29.0 `ExactSvmScheme.createPaymentPayload` always appends a Memo instruction
(`MemoSq4gqABAXKb96qnH8TysNcWxMyWCqXgDLGmfcHr`, no accounts): the seller's `extra.memo` if given, else a
random 16-byte hex nonce. Source: `node_modules/@x402/svm/dist/esm/chunk-VJYARVT4.mjs`, around
`memoIx`. `inspectTransfer` treats any program off its list as `UNKNOWN_PROGRAM_DETECTED`, so it
refuses every payment the SDK builds.

I ran the real SDK against a fake RPC and fed its transaction to `inspectTransfer`: the result is
exactly `['UNKNOWN_PROGRAM_DETECTED']`. The transfer, compute budget (limit 20 000, price 1
microlamport) and fee payer all pass. Test: `packages/guard-core/test/svm-x402.test.ts`.

**Ask:** allow the Memo program with zero accounts and data of at most 256 bytes (the SDK's own
`MAX_MEMO_BYTES`), at most once per transaction. Anything else about it stays a reason to refuse.
When it lands, my pinned test fails and I flip it to expect a signed payload.

Also for SVM-3: CR-003 in `/CHANGES_REQUESTED.md` proposes `ChainAdapter.x402Scheme(intent,
requirements)`. The Solana implementation already exists in
`packages/guard-core/src/adapters/svm-x402.ts`, ready to move to `svm/` if approved.

Note on fee payer: in exact SVM the facilitator pays the fee and names its key in
`extra.feePayer`, so guard-core passes that key as `ExpectedTransfer.feePayer`, not the hot wallet.
