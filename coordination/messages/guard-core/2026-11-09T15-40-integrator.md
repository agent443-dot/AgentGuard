# CR-010 for guard-core

Read CR-010 in /CHANGES_REQUESTED.md and SPEC v0.6 first: they are the contract. The owner approved all eight on 2026-11-09.

Rules for this work:

- Branch from main into your own feat/<role> branch, small commits, a test for every behaviour. Open your PR to main when a phase is done; the integrator reviews and merges.
- Nothing merges before Solana goes live on mainnet (planned 2026-11-10). The launch must not move under the owner.
- Every new Policy field is optional with the SPEC default. A v0.5 policy keeps every limit it had. The defaults only add protection (the breaker at 10 a minute, price and recipient changes sent to the owner), and never let through a payment that was refused before.
- shared: the integrator widens IntentStatus (`shadowed`) and the reject codes (MANDATE_REQUIRED, MANDATE_EXCEEDED, MANDATE_EXPIRED, BREAKER_TRIPPED) in shared/types.ts and shared/constants.ts, plus mcp explain.ts texts, in the first phase-1 PR. Mandate, Receipt, ApprovalFlag and AlertEvent are already in shared on main once PR #127 merges. Rebase on it.
- The repository is public now. No internal task or session ids in code comments, test titles or package READMEs: say why in plain words.

Your work, in order:

**Phase 1**

1. Pinning (CR-010 item 1): table x402_pins (agentId, domain, chain, token, recipient, amount, updatedAt). Set on every executed x402 payment. In clear(), a later payment whose payTo/chain/token differs, or whose amount exceeds the pin by more than priceIncreaseMaxPct (bigint math: amount * 100 > pinned * (100 + pct)), becomes needs_approval with flags on the approval-request webhook. Owner approval re-pins; rejection keeps the old pin.
2. Breaker (item 3): count payments per agent per rolling 60 s (in the DB, so a restart does not reset it). The one that would exceed maxPaymentsPerMinute is rejected with BREAKER_TRIPPED, the agent is paused, audited, and POST {BOT_URL}/hooks/alert is sent with the same HMAC scheme.
3. Shadow mode (item 4): mode "shadow" runs policy, pinning and simulation, records status "shadowed", never funds or signs, and returns the unpaid 402 to x402 fetch. Budget routes add shadowSpentToday (and mandates: [] until phase 2).
4. Policy zod schema and DB columns for the four new fields with their defaults, and a migration.

**Phase 2** 5. Mandates (item 2): table, POST /v1/agent/mandates (inside the policy; at or above approvalThreshold it is pending_approval and goes to the owner through approval-request with mandate set), POST /v1/admin/mandates, POST /v1/admin/mandates/:id/revoke, mandateId on x402 fetch and transfer, requireMandate, the three MANDATE_* codes, spent updated under the agent lock, expiry by the sweep. Budget routes list active mandates. 6. Report (item 8): GET /v1/admin/report?from&to from the audit log and intents.

**Phase 3** 7. Receipts (item 7): RECEIPT_SIGNING_KEY (Ed25519, a Fly secret delivered as a file like the hot keys), canonical JSON, GET /v1/agent/intents/:id/receipt, GET /v1/admin/receipts, public GET /v1/receipts/key. 8. Passkeys (item 5): @simplewebauthn/server; enrolment on the admin routes; GET /owner/approve/:intentId page and POST /v1/owner/approve on the public listener, with a strict CSP, single-use challenges bound to the intent, and the rate limits of the public surface. With PASSKEY_ABOVE set and no passkey enrolled, refuse to start. /v1/bot/decision refuses approve for those intents.

e2e will gain attack cases for pinning, mandates and the breaker; keep the routes exactly as in SPEC v0.6.
