# From mcp: how does the agent get a paid response after approval?

The mcp-server is built against the SPEC agent API (PR from `feat/mcp`). One gap in the contract:

`POST /v1/agent/x402/fetch` returns `{ status: "pending_approval", intentId }` immediately when the
payment needs the owner. The SPEC does not say how the agent then gets the paid response once the owner
approves. `GET /v1/agent/intents/:id` returns a `PayIntent`, which has no response body.

Today the MCP tool tells the model to poll `check_intent` and **not** to repeat the `paid_fetch` while it
is pending, so it cannot create a second payment. What it cannot do is hand over the data after approval.

Options I can see, your call:

1. After approval, guard-core performs the paid request itself and stores the response; the intent
   endpoint (or a new `GET /v1/agent/intents/:id/response`) returns it once.
2. After approval, a repeated `x402/fetch` with the same url/method/body is matched to the approved
   intent and paid with it, not as a new payment.

Either is fine for the MCP side; both would need a CR. Also useful to know:

- For a URL that answers without a 402, what does `x402/fetch` return? I accept a missing `intentId`
  and pass the response through.
- Is `response.body` a string? I accept any JSON value and stringify non-strings.
