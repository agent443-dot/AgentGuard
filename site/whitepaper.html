Whitepaper

The security layer every agent needs.

AgentGuard Version 0.5 November 2026 Live on mainnet

AgentGuard is a security layer between an AI agent and its wallet, a firewall for autonomous payments. An agent can only pay through AgentGuard. Every payment is checked against a policy the owner sets, test-run before it is signed, and then auto-approved, sent to the owner on Telegram for approval, or rejected. The agent never holds a key. Funds stay in the owner's own multisig vault; the agent spends only from a small hot wallet that is refilled under a daily limit enforced by the blockchain itself, so the maximum that can be lost in a day is bounded even if our software fails.

01The problem

Autonomous agents are starting to move money: paying per-request APIs, settling invoices, buying compute. The moment an agent can spend, a single bad instruction, a prompt injection, a bug or a compromised key can drain a wallet in seconds. Handing an agent a private key trades all of your funds for a little convenience.

AgentGuard removes that trade-off. The agent gets spending power; you keep the keys and a hard ceiling on what can go wrong.

02Architecture

Money flows through four layers. Each one narrows what the one above it can do.

Owner multisig vault — holds the funds. Squads v4 on Solana, Safe on EVM chains. Only the owner controls it.
Onchain spend limit — refills the hot wallet, never above the daily cap. enforced by the chain, not by us
Guard hot wallet — a small balance the agent spends from. Its key lives only inside the guard service, never logged, never returned.
Payments — x402 pay-per-use APIs and transfers, only to recipients and domains the owner allowed.

The agent talks to AgentGuard over the Model Context Protocol (MCP), so one connection works with any agent on any platform. Four tools are exposed: paid_fetch, transfer, get_budget and check_intent. The guard never imports a chain SDK directly; each chain sits behind a single adapter interface, so every chain gets the same policy, the same test run and the same kill switch.

03Onchain guarantees

The spend limit is a primitive that is already audited and deployed: the Squads Spending Limit on Solana, and the Safe Allowance Module (reset every 24 hours) on EVM chains. AgentGuard deploys no smart contract of its own. The vault refills the hot wallet up to a daily cap and no more, and the chain enforces that regardless of what our software does.

Maximum loss per day = daily cap + hot wallet balance.

This holds even if the offchain guard has a bug or is fully compromised. At launch the cap is deliberately low and raised only after weeks without incident. A kill removes the limit entirely and is signed by the owner.

04The policy engine

Before anything is signed, every payment is checked against the agent's policy. A new agent starts at deny-all and can spend nothing until the owner allows it.

  • Per-payment and daily limits — a hard ceiling on each payment and on the day's total, beneath the onchain cap.
  • Allowlists — which chains, tokens, recipients and API domains are permitted. Empty means deny.
  • Approval threshold — any payment at or above it waits for the owner on Telegram.
  • Pause — one switch stops an agent, or every agent at once.

Agent-provided text, the reason it gives, the URL, an API response, is shown to the owner but never used to make a decision. Amounts are integers in the token's smallest unit end to end; a value that would need rounding is refused, never rounded.

05Simulation and threat detection

A payment that passes policy is test-run against the real chain before signing. The guard inspects the exact transaction, sees what it would actually do, and refuses anything that differs from the approved intent, with a named reject code written to the audit log.

Scope Reject code Meaning
All chains PER_TX_EXCEEDED · DAILY_EXCEEDED Over a limit you set.
All chains RECIPIENT_NOT_ALLOWED · DOMAIN_NOT_ALLOWED A destination you did not approve.
All chains SIM_UNEXPECTED_EFFECT The test run shows an effect the intent never described.
Solana DELEGATE_DETECTED · AUTHORITY_CHANGE_DETECTED A hidden permission grab or an account takeover.
EVM APPROVAL_DETECTED · PERMIT_DETECTED A hidden token approval or a signature that would allow later withdrawals.

Twenty reject codes in all, split into a shared core and per-chain sets. Default deny: any parsing doubt is a rejection.

06Human approval and the kill switch

Payments at or above your threshold are sent to Telegram with a plain summary of what the transaction will do. You approve or reject. An approval is redeemed once, for exactly the approved chain, token, amount, recipient and domain, and expires after ten minutes if you do not answer, so nothing is paid by default. Every message to the bot is cryptographically signed; stale or replayed events are refused.

One command, /kill, pauses every agent at once and prepares, for each chain, the transaction that sets the spending limit to zero and removes the delegate. You sign it and the vault is sealed. The kill has been rehearsed on mainnet.

O AgentGuard é uma camada de segurança entre um agente de IA e a carteira dele, um firewall para pagamentos autônomos. O agente só consegue pagar através do AgentGuard. Cada pagamento é verificado contra uma política definida pelo dono, testado antes de ser assinado e então aprovado automaticamente, enviado ao dono no Telegram para aprovação, ou recusado. O agente nunca guarda uma chave. Os fundos ficam no cofre multisig do próprio dono; o agente gasta apenas de uma pequena carteira de uso, reabastecida sob um limite diário imposto pela própria blockchain, de modo que a perda máxima em um dia é limitada mesmo que o nosso software falhe.

01O problema

Agentes autônomos estão começando a movimentar dinheiro: pagar APIs por requisição, quitar faturas, comprar poder computacional. No momento em que um agente pode gastar, uma única instrução ruim, uma injeção de prompt, um bug ou uma chave comprometida pode drenar a carteira em segundos. Entregar uma chave privada a um agente troca todos os seus fundos por um pouco de conveniência.

O AgentGuard elimina essa troca. O agente ganha poder de gasto; você mantém as chaves e um teto rígido para o que pode dar errado.

02Arquitetura

O dinheiro passa por quatro camadas. Cada uma restringe o que a camada acima pode fazer.

Cofre multisig do dono — guarda os fundos. Squads v4 na Solana, Safe nas redes EVM. Só o dono o controla.
Limite de gasto onchain — reabastece a carteira de uso, nunca acima do teto diário. imposto pela blockchain, não por nós
Carteira de uso do guard — um saldo pequeno de onde o agente gasta. A chave dela vive apenas dentro do serviço, nunca é registrada nem devolvida.
Pagamentos — APIs x402 por uso e transferências, apenas para destinatários e domínios que o dono permitiu.

O agente conversa com o AgentGuard pelo Model Context Protocol (MCP), então uma única conexão funciona com qualquer agente em qualquer plataforma. Quatro ferramentas são expostas: paid_fetch, transfer, get_budget e check_intent. O guard nunca importa um SDK de blockchain diretamente; cada rede fica por trás de uma única interface de adaptador, de modo que toda rede recebe a mesma política, o mesmo teste prévio e o mesmo botão de desligar.

03Garantias onchain

O limite de gasto é uma primitiva já auditada e implantada: o Squads Spending Limit na Solana e o Safe Allowance Module (reinicia a cada 24 horas) nas redes EVM. O AgentGuard não implanta nenhum contrato próprio. O cofre reabastece a carteira de uso até um teto diário e nada além disso, e a blockchain impõe esse limite independentemente do que o nosso software faça.

Perda máxima por dia = teto diário + saldo da carteira de uso.

Isso vale mesmo que o guard offchain tenha um bug ou seja totalmente comprometido. No lançamento o teto é propositalmente baixo e só é elevado após semanas sem incidentes. Um kill remove o limite por completo e é assinado pelo dono.

04O motor de políticas

Antes de qualquer assinatura, todo pagamento é verificado contra a política do agente. Um agente novo começa em negar-tudo e não pode gastar nada até que o dono permita.

  • Limites por pagamento e por dia — um teto rígido para cada pagamento e para o total do dia, abaixo do teto onchain.
  • Listas de permissão — quais redes, tokens, destinatários e domínios de API são permitidos. Vazio significa negar.
  • Limiar de aprovação — qualquer pagamento igual ou acima dele espera pelo dono no Telegram.
  • Pausa — um botão para um agente, ou para todos de uma vez.

O texto fornecido pelo agente, a razão que ele dá, a URL, a resposta de uma API, é mostrado ao dono mas nunca usado para decidir. Os valores são inteiros na menor unidade do token de ponta a ponta; um valor que exigisse arredondamento é recusado, nunca arredondado.

05Simulação e detecção de ameaças

Um pagamento que passa pela política é testado contra a rede real antes de ser assinado. O guard inspeciona a transação exata, vê o que ela realmente faria e recusa qualquer coisa que difira da intenção aprovada, com um código de recusa nomeado gravado no log de auditoria.

Escopo Código de recusa Significado
Todas as redes PER_TX_EXCEEDED · DAILY_EXCEEDED Acima de um limite que você definiu.
Todas as redes RECIPIENT_NOT_ALLOWED · DOMAIN_NOT_ALLOWED Um destino que você não aprovou.
Todas as redes SIM_UNEXPECTED_EFFECT O teste revela um efeito que a intenção nunca descreveu.
Solana DELEGATE_DETECTED · AUTHORITY_CHANGE_DETECTED Uma permissão oculta ou a tomada de uma conta.
EVM APPROVAL_DETECTED · PERMIT_DETECTED Uma aprovação de token oculta ou uma assinatura que permitiria saques depois.

Vinte códigos de recusa no total, divididos em um núcleo comum e conjuntos por rede. Negar por padrão: qualquer dúvida na leitura é uma recusa.

06Aprovação humana e o botão de desligar

Pagamentos iguais ou acima do seu limiar são enviados ao Telegram com um resumo claro do que a transação fará. Você aprova ou recusa. Uma aprovação é usada uma única vez, exatamente para a rede, o token, o valor, o destinatário e o domínio aprovados, e expira após dez minutos se você não responder, de modo que nada é pago por padrão. Toda mensagem ao bot é assinada criptograficamente; eventos antigos ou repetidos são recusados.

Um comando, /kill, pausa todos os agentes de uma vez e prepara, para cada rede, a transação que zera o limite de gasto e remove o delegado. Você assina e o cofre é lacrado. O kill já foi ensaiado em mainnet.

AgentGuard es una capa de seguridad entre un agente de IA y su billetera, un firewall para pagos autónomos. Un agente solo puede pagar a través de AgentGuard. Cada pago se verifica contra una política que define el dueño, se prueba antes de firmarse y luego se aprueba automáticamente, se envía al dueño por Telegram para su aprobación, o se rechaza. El agente nunca tiene una clave. Los fondos permanecen en la bóveda multisig del propio dueño; el agente solo gasta de una pequeña billetera de uso, recargada bajo un límite diario que impone la propia blockchain, de modo que la pérdida máxima en un día está acotada aunque nuestro software falle.

01El problema

Los agentes autónomos empiezan a mover dinero: pagar APIs por solicitud, liquidar facturas, comprar cómputo. En el momento en que un agente puede gastar, una sola instrucción maliciosa, una inyección de prompt, un error o una clave comprometida puede vaciar una billetera en segundos. Entregar una clave privada a un agente cambia todos tus fondos por un poco de comodidad.

AgentGuard elimina ese dilema. El agente obtiene poder de gasto; tú conservas las claves y un techo rígido sobre lo que puede salir mal.

02Arquitectura

El dinero pasa por cuatro capas. Cada una limita lo que puede hacer la capa superior.

Bóveda multisig del dueño — guarda los fondos. Squads v4 en Solana, Safe en cadenas EVM. Solo el dueño la controla.
Límite de gasto onchain — recarga la billetera de uso, nunca por encima del tope diario. lo impone la cadena, no nosotros
Billetera de uso del guard — un saldo pequeño del que gasta el agente. Su clave vive solo dentro del servicio, nunca se registra ni se devuelve.
Pagos — APIs x402 de pago por uso y transferencias, solo a destinatarios y dominios que el dueño permitió.

El agente se comunica con AgentGuard mediante el Model Context Protocol (MCP), así que una sola conexión funciona con cualquier agente en cualquier plataforma. El guard nunca importa un SDK de cadena directamente; cada cadena está detrás de una única interfaz de adaptador, de modo que toda cadena recibe la misma política, la misma prueba previa y el mismo interruptor de apagado.

03Garantías onchain

El límite de gasto es una primitiva ya auditada y desplegada: el Squads Spending Limit en Solana y el Safe Allowance Module (se reinicia cada 24 horas) en cadenas EVM. AgentGuard no despliega ningún contrato propio. La bóveda recarga la billetera de uso hasta un tope diario y no más, y la cadena impone ese límite sin importar lo que haga nuestro software.

Pérdida máxima por día = tope diario + saldo de la billetera de uso.

Esto se cumple aunque el guard offchain tenga un error o esté totalmente comprometido. En el lanzamiento el tope es deliberadamente bajo y solo se eleva tras semanas sin incidentes. Un kill elimina el límite por completo y lo firma el dueño.

04El motor de políticas

Antes de firmar nada, cada pago se verifica contra la política del agente. Un agente nuevo empieza en negar-todo y no puede gastar nada hasta que el dueño lo permita.

  • Límites por pago y por día — un techo rígido para cada pago y para el total del día, por debajo del tope onchain.
  • Listas de permitidos — qué cadenas, tokens, destinatarios y dominios de API se permiten. Vacío significa negar.
  • Umbral de aprobación — cualquier pago igual o superior espera al dueño en Telegram.
